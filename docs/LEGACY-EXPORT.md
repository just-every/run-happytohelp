# Export legacy HappyToHelp

This operator tool reads one explicitly chosen legacy MySQL project and its media. It makes no source writes, discovers no credentials and never loads dotenv files. It belongs beside the native importer; it does not use a web endpoint or change an installation. Run Node 22.20.0, `pnpm install --frozen-lockfile`, and AWS CLI v2 for direct S3 reads.

## Access and extraction

Supply `LEGACY_MYSQL_HOST`, `LEGACY_MYSQL_PORT` (default 3306), `LEGACY_MYSQL_DATABASE`, `LEGACY_MYSQL_USER`, `LEGACY_MYSQL_PASSWORD` in the process environment. Use a local SSH tunnel to a private database or `LEGACY_MYSQL_SSL_CA` for verified MySQL TLS. Use a SELECT-only database account. The tool sets UTC and repeatable-read, opens a consistent read-only transaction, reads every SELECT on that connection, then commits. Tables keyed by `id` are read in id-ordered pages of 10,000 rows inside that transaction, so a slow tunnel never has to buffer a whole table; other tables stream in one result. It requires InnoDB for every table it reads. No lock, write, schema change, dump privilege, superuser, SSH key or AWS discovery permission is needed.

```sh
node scripts/export-legacy.mjs snapshot \
  --project PROJECT_UUID --revision LEGACY_GIT_SHA --ai-model gpt-5.6-luna \
  --mail-from-domain LEGACY_MAIL_FROM_DOMAIN \
  --output exports/company.snapshot.json
```

Supply the legacy installation’s `MAIL_FROM_DOMAIN` as `--mail-from-domain`; project inbound addresses are `slug@mail.<domain>`. It is separate from the project website and sender address. The wrapper takes it from `LEGACY_MAIL_FROM_DOMAIN`. Choose the native AI model explicitly. The legacy `ais` table has no model field; the example is the native edition's configured OpenAI default, not a recovered historical model. No provider work runs during import.

The snapshot retains UUIDs, all selected noncredential columns, SQL decimals/BIGINTs as strings, JSON as JSON, and UTC timestamps. It includes direct project tables, conversation children, article/category pivots, dataset files, referenced human/AI authors, matching global AI defaults, scoped polymorphic media and image variants. It fails for unclassified tables instead of silently claiming to export them. The current scope and credential omissions are in `scripts/legacy-export/scope.mjs`. Secret-like column names and content require explicit classification in `secrets.mjs`: nested JSON (including JSON in TEXT), credential assignments, provider tokens, hashes and encrypted-looking payloads fail closed before publication. Widget cache checksums and numeric provider token counts have narrow export classifications. A new unknown secret-like field stops the export; errors name the source column without printing its value. The attachments step also refuses old or edited snapshots containing omitted fields. The integration schema includes the 53-table live shape captured on 16 October 2026, including the newer local-computer/delegation and refresh fields.

Passwords, remember/invitation/contact-key tokens, verification/shared keys, their crypto-only references and GitHub access tokens are omitted. `collector_actions.action` is dropped: it is encrypted visitor telemetry whose key is deliberately omitted, and retaining it has no support-history use. Nothing decrypts or archives that payload. Raw crawler HTML, crawler exception text, encrypted actions, captured page HTML, collected browsing payloads/summaries and raw MIME transport are omitted: these duplicate rendered content/verified attachments or repeat visitor URL credentials. Their non-payload metadata remains archived. The known `contacts.metadata.admin` capability URL and `conversations.metadata.customer_reply` and `.suggestions` runtime trigger/composer caches are removed explicitly and counted in the manifest; unknown nested secret fields still stop export. Browser user-agent headers are omitted as visitor telemetry. Reviewed credential assignments, authentication signatures, HTTP cookies, hidden authentication form values, HAR headers and URL capability values in rendered support text are replaced by `<redacted>` and counted. These include prefix-typed `sk_`/`rk_` keys (also with Markdown's escaped underscore), `curl -u user:secret` and `-u key:` Basic credentials, URL userinfo with or without a user (`redis://:password@host`), unquoted credential values up to the next space, 2FA setup keys written in 4-character groups and `pwd` meeting links. Provider tokens and webhook links are recognized by their own prefix or host (Slack, Shopify, GitLab, HubSpot, Google, npm, Atlassian, Square, Braintree, Mailgun, Mailchimp, Telegram and Discord forms), with no label needed. Cookies in HAR fragments that are not complete JSON and in `curl -b` are removed. A `curl -u` value is kept only when it is an explicit documentation placeholder (`<TOKEN>`, `$VAR`, `YOUR_…`, `XXXX`, or an environment variable name such as `STRIPE_SECRET_KEY`), never because it is written in capitals. Passwords in prose ("my password is …"), under short or translated names (`pass:`, `pw:`, `Passwort:`, `contraseña:`), application passwords in 4-character groups and 2FA keys after "key" are removed. Sign-in, reset, verification and invitation links lose their capability segment, and a private key cut off before its END line goes whole. When a removed value ends at a line break, the line that continues it is removed too; after a marker already in the text, only key-shaped continuation lines are. A value removed in one place is removed wherever the project's text repeats it, and so is every 16+ character token inside it. Opaque runs of 32 or more characters are judged against the entropy a random string of that length would show, which removes about 99% of random mixed-case secrets while word, number and date slugs stay readable. Unverified opaque URLs are omitted as potential access capabilities; documented public avatar, video, document and integration-invitation identifiers remain references. Unclassified opaque diagnostic values are omitted as potential credentials too; their omission counts are explicit. Unknown assignments, JSON fields and encrypted envelopes still fail closed. Braintree authentication/payment nonce fields are omitted; its [public client configuration IDs](https://developer.paypal.com/braintree/graphql/reference/) remain identifiers. [Gravatar hashes](https://docs.gravatar.com/rest/hash/) are public avatar identifiers; [Google Drive resource keys](https://developers.google.com/workspace/drive/api/guides/resource-keys) remain omitted access capabilities. Code variable references and explicit documentation placeholders remain readable. Reviewed public asset identifiers, Gravatar email digests, AI evidence checksums and numeric cache token counters have narrow noncredential classifications. Opaque provider continuation IDs/signatures in `message_thinkings.thinking_id` and `message_thinkings.signature` are also omitted; they are unnecessary to read the retained conversation. Asymmetric/contact shared-key tables, auth resets, queues, Telescope and the unrelated waitlist are excluded. The snapshot records names of excluded tables and omitted columns. Other original business fields remain in the importer's archive, including unsupported fields and soft-deleted records.

## Attachments

```sh
# Directory must contain the original bucket's key tree (not renamed files).
node scripts/export-legacy.mjs attachments \
  --input exports/company.snapshot.json --objects-dir /private/copied-bucket \
  --output exports/company.import.json

# Or read only the exact S3 keys from the snapshot.
node scripts/export-legacy.mjs attachments \
  --input exports/company.snapshot.json --bucket CONFIRMED_BUCKET --region us-east-1 \
  --output exports/company.import.json
```

S3 uses only `s3:GetObject` through AWS CLI `s3api get-object`, with explicit `LEGACY_AWS_ACCESS_KEY_ID`, `LEGACY_AWS_SECRET_ACCESS_KEY` and optional `LEGACY_AWS_SESSION_TOKEN`. It ignores existing AWS profiles/config and never lists or writes the bucket. Add `kms:Decrypt` for the specific KMS key only if these objects use SSE-KMS. Local `public` media must be supplied from its filesystem root; other disks fail explicitly. Missing objects and wrong sizes fail. Bytes are base64 encoded with SHA-256 and copied into native local R2 by the importer. Original S3 keys, filenames and media joins stay in the artifact. Non-message media is retained in R2/archive; inline article images and logos still need the separate URL-rewrite work described below.

For production-sized projects use directory output:

```sh
node scripts/export-legacy.mjs snapshot --project PROJECT_UUID --revision LEGACY_REVISION \
  --ai-model gpt-5.6-luna --mail-from-domain LEGACY_MAIL_FROM_DOMAIN \
  --chunk-bytes 4194304 --output /private/company/snapshot
node scripts/export-legacy.mjs attachments --input /private/company/snapshot \
  --bucket CONFIRMED_BUCKET --region us-east-1 --output /private/company/import
node scripts/import-legacy.mjs --package /private/company/import --apply --persist-to .wrangler/state
```

To import a package into a deployed installation's own D1 and R2 with its deploy credentials, use `--remote --database <d1> --bucket <r2>` instead of `--persist-to`; see [Legacy data import](../src/modules/legacy-import/README.md).

The wrapper uses this format. Rows stream into bounded JSON chunks (4 MiB by default; a larger individual row fails explicitly). Media streams into separate binary files with exact byte counts and SHA-256; aggregate media has no JSON/base64 or heap-size limit. Import verifies every chunk, count and object, and runs the export validator on every part, before writing. It then imports rows in dependency order and writes objects to R2 in bounded multipart chunks. Local apply holds an exclusive persistence lock. The cross-table context (transcript revisions, deleted parents, attachment associations, contact identities) lives in a private on-disk index, so memory does not grow with the project. Imported credentials remain revoked and running work is held. Replaying the same package resumes the exact chunk runs; unchanged exports retain canonical identity.

The manifest records exported counts and independent SQL counts from the same read-only snapshot. Both must match. `LEGACY_MYSQL_EXPECTED_SERVER_PREFIX` optionally checks Aurora identity before starting; the clone run requires `hh-export-clone-`. `--defer-mail-domain` explicitly records missing mailbox configuration without inventing an address. Such a package still imports: the legacy sender name and address are kept, no inbound address is created, email stays disabled, and a `legacy_import_holds` row asks the operator to set and verify the domain before enabling email. Imported mail settings are always disabled, because nothing here can verify them. Default snapshot behavior still requires the domain.

The original single-file format retains its bounds: 256 MiB of row JSON, 256 MiB of raw attachments and 512 MiB of final JSON. Increase only with an explicit `--max-row-bytes`, `--max-object-bytes`, or `--max-json-bytes` byte count and adequate local memory. These single-file memory bounds do not apply to the directory format; use chunks for large projects. There is no silent truncation.

Outputs are private (0600), exclusively created and published after success. Existing files are never replaced. Snapshot extraction must restart after interruption; the consistent transaction cannot resume on a later connection. The completed snapshot is immutable. Retry only the attachments step from it with a new output path. Attachment copying is read-only and may safely repeat; it has no durable byte cache. Import resumes per row from the exact final artifact.

For an owner-run export in a checkout already on `hh/legacy-export`, with the environment above plus `LEGACY_S3_BUCKET`, `LEGACY_AWS_REGION` and `LEGACY_MAIL_FROM_DOMAIN`:

```sh
bash scripts/legacy-export/export-project.sh PROJECT_UUID LEGACY_GIT_SHA gpt-5.6-luna exports/company
```

Run once per project into a distinct directory. The resulting `import/` and `snapshot/` packages contain private support data: transfer them through the owner's private channel, never Git or a public PR.

## Re-pass an exported package

When the text policy changes after an export, apply it to the exported rows instead of reading the source again:

```sh
node scripts/export-legacy.mjs repass --input /private/company/import \
  --policy-revision EXPORTER_GIT_SHA --output /private/company-v2/import
```

The input is only read. Each part is rewritten with the same rows, validated and digested again; values the policy now removes are also removed wherever the package repeats them. Attachments are hard-linked byte-identical and checked by size and SHA-256. The manifest keeps its counts, adds the new omissions to its totals and records the run under `source.textPolicyRepasses`. Re-pass `snapshot/` the same way. Its parts must equal `import/`'s.

## Independent package scan

```sh
node scripts/scan-legacy-package.mjs /private/company-v2
```

`scripts/legacy-scan/` shares no rule or placeholder list with the text policy, so a miss in one is caught by the other. It checks every byte of every file for provider and transport signatures, and every decoded row and context string for labelled values, cookies, wrapped remnants, sign-in links and opaque runs. It writes `secret-signatures.json` (kinds, files, row ids and masked shapes) and fails on any hit in rows, context, manifests or logs. Attachments and their file names are customer originals outside the text policy: their signatures are listed by kind and file for the operator and do not decide the scan.

## Native import

Use an isolated native checkout. Start local state/migrations through `rer dev`, then stop it before importing; alternatively prepare/apply local migrations directly. Keep the completed artifact for resume.

```sh
pnpm run migrations:prepare
pnpm exec wrangler d1 migrations apply DB --local --persist-to .wrangler/state
node scripts/import-legacy.mjs --file exports/company.import.json
node scripts/import-legacy.mjs --file exports/company.import.json --apply --persist-to .wrangler/state
```

The plan is read-only. Apply writes only local D1/R2. Bundle digest is the run identity; source rows and canonical writes commit together. Exact replay skips every completed row. A new full artifact must match existing canonical bytes or stops without overwriting them. Earlier committed rows remain after a later conflict; resume the exact artifact. A full package is a migration and replay; what legacy takes after its export arrives through [delta sweeps](#delta-sweeps), which apply legacy changes only where the seed has not changed the row. Neither is a cutover procedure.

**Imported history is history, not work.** A full package (or `--file` export) leaves the installation's work as it found it:

- **No trigger-written work rows.** Each batch removes the rows the application's own triggers add as a side effect of the import (integration events such as `contact.created`, `conversation.status_changed` and `article.published`, the workflow journal, mail and notification work, resolutions, and the waiting-visitor set), keeping only rows from before the batch, so `check.mjs work` counts (which include `workflow_events`) are unchanged and no fan-out, scheduler or survey dispatcher finds work the import caused.
- **The default rule stays a draft.** Every new workspace is born with the published time rule "Close solved tickets after 4 days". A legacy workspace never had it, and a first scheduler run would close its imported solved conversations (closed is final). An imported workspace gets that rule as an unpublished draft with no published version; publish it from the workflow page when you want it. `--publish-default-rules` keeps it published, as a new workspace has it. Legacy has no workflow rules of its own, so none are imported.
- **Imported conversations open read.** Unread is each team member's work queue, so every conversation the import inserts is marked read, up to its last message, for each member the workspace has (members are imported before conversations); old reads themselves are not replayed. `--leave-unread` leaves them unread as a native conversation would be. A delta sweep never marks anything read: what legacy took after the export is work for the team. Someone added to the workspace after the import sees the history as any new member sees a workspace's conversations.
- **Authorless messages are the workspace speaking.** A legacy message with no author at all (for example ChargeDesk's automatic away text) is imported with role `system`, as native away replies are, and the actor `legacy-system`; it is never an operator's reply. Every imported message also gets a `message_authorship` row where the kind follows from what legacy recorded: `visitor` for a contact's message, `ai` for an AI's, `human` for an agent's, and `unknown` otherwise (system text); no drafting or handoff history is guessed. An import that had already written messages in the earlier form stops on the conflict check rather than overwriting them.

Native mappings preserve conversation/message/note/contact/article/category/macro IDs. Local-agent identity JSON, media alt text and global inbox appearance have no corresponding persisted native field and remain archived. Refresh preferences and successful refresh time survive; pending claims, crawl webhook tokens and credentials are omitted, and scheduled paid work is held.

Internal notes come from `events.type=INTERNAL_NOTE` and remain private. Draft categories use nullable `published_at`; deleted records are archive-only, including dependent transcripts. Preferred contact name/email and original file names survive. Invitees with no user stay archive-only. Old credentials are not native logins; recover/pair/reconnect through native flows separately.

Project `website` supplies the allowed origin. Raw widget/availability settings, responder IDs, timezone, help-center HTTPS URL and logo URL are retained in project settings. Category order/nesting, crawl exclusions and limits, closed insight state, disabled sender/mailbox settings and project slug aliases map into native live fields; unsupported legacy widget defaults, proxy controls and billing fields remain archived. This does not configure DNS, sending domains, mail credentials, providers or legacy-widget compatibility.

## Delta sweeps

Legacy keeps taking chats and mail until the company's widget and mail move to the seed, and for a few quiet days after. Sweep everything it took since the last export into the seed, as often as needed, until the legacy project is retired.

**Watermark.** Every export, full or delta, records `source.watermark` in its manifest: the legacy database's own clock (`UTC_TIMESTAMP`), read as the first statement inside its consistent snapshot, less a 300-second overlap (`source.watermarkOverlapSeconds`; the raw read is `source.snapshotClock`). A row a request stamped just before the snapshot began but committed after it is re-included by the next delta instead of missed, and the import makes a re-included row a no-op. The next delta passes the previous export's watermark as `--since`.

```sh
node scripts/export-legacy.mjs snapshot --project PROJECT_UUID --revision LEGACY_REVISION \
  --ai-model gpt-5.6-luna --mail-from-domain LEGACY_MAIL_FROM_DOMAIN \
  --chunk-bytes 4194304 --since PREVIOUS_WATERMARK --output /private/company/delta-1/snapshot
node scripts/export-legacy.mjs attachments --input /private/company/delta-1/snapshot \
  --bucket CONFIRMED_BUCKET --region us-east-1 --output /private/company/delta-1/import
```

**Delta export.** `--since` takes an ISO-8601 UTC time (`2026-11-08T09:30:00Z`) and writes only the chunked directory format, so it requires `--chunk-bytes`; `attachments` and `repass` take the delta package as `--input` and refuse `--since`. A delta reads the same whole project scope as a full export in the same kind of snapshot: the credential pre-scan, every classification, the count guards (`cloneCounts`, and `scopedCounts` for the whole scope) and the mapping context stay whole. Its row chunks carry only rows whose `created_at`, `updated_at` or `deleted_at` is at or after `--since` (`events` have only `created_at`), plus what the import needs to apply them: the parent conversation of every changed message, event, participant, bucket and message file, the users those rows name, and the `mediables` pivots of changed media. `source.rowCounts` counts the chunk rows and `source.since` marks the package as a delta. Context parts carry every row of the context tables, message delivery ids included, except media: a delta's media context, and so its `attachments` step, is its changed media alone.

**The first delta's `--since`.** Use the full package's `source.watermark`. A package exported before watermarks were recorded has none: use a time at or before that package's snapshot, for a package exported from a database clone the clone's creation time, otherwise its `source.exportedAt` less the time the export ran. Earlier is always safe; a later time can miss rows.

**Installations imported before delta state.** For every canonical row it writes or confirms, the importer records the digest of what it wrote and of the legacy row it came from (`legacy_import_state`, migration `307_legacy_import_delta.sql`). An installation imported before that has no record, so a delta would list every existing row it touches as a conflict. Once, before its first delta, apply the installation's original package again with the same command (`--persist-to` or `--remote` as before). It is an exact replay: every row is already journaled, no business row or file changes, and it records state for each row that still equals its import. A row the seed has changed since gets none and stays as the seed has it. The journal's index by source row comes from migration `306_cutover_steps.sql`.

**Import.** `node scripts/import-legacy.mjs --package /private/company/delta-1/import --apply` with `--persist-to` or `--remote --database --bucket`, as for a full package, recognises a delta from `source.since`. It first takes the workspace's lease, so it never writes while a contact of the workspace is being erased: while an erasure runs it waits (one `{"step":"waiting","for":"erasure"}` progress line on stderr every 30 seconds, counts only) for up to 15 minutes and then exits non-zero having written nothing, to be run again. A full package and a `--file` export take the same lease the same way (they name the workspace in `source.projectId`, as every export does; one without it is refused before any write), and treat erased contacts as a delta does: their rows are journaled with `source_json='{}'`, status `erased` and the target they map to, nothing else of theirs is written, and their files are not uploaded. It holds the lease, renewed every 20 seconds, until its last write, uploads included; every batch confirms it and every upload confirms it before and after, so a run that stalled past its lease's one-minute expiry keeps nothing more (an upload that landed after the lapse is deleted again, and each upload is recorded in `legacy_import_objects` only in a batch that confirms the lease) and stops with a message to run the same command again. A file of an erased contact that an earlier run uploaded before her erasure could see it (her file row not journaled yet) is deleted from R2 by the next run, with that run's record of it; one her erasure already removed stays removed, its record kept, and one the workspace holds as another person's attachment stays, as her erasure keeps it. A file is an erased contact's as her erasure decides it: one the import puts in a conversation (its own, or its message's) is that conversation's customer's and its uploader's, so a file of another customer's conversation that legacy also links into hers is imported for that customer in every order (an erasure between a stopped run and its rerun included); only a file with no conversation of its own goes with everyone it is linked to. In turn, an erasure requested while a delta applies waits up to 30 seconds and then answers 409 with `Retry-After`, so run sweeps when nobody is erasing contacts. Before its first write it plans across every chunk and checks every chunk and attachment read-only. Then, per mapped row:

- a row the seed does not have is appended;
- a row already equal to the new mapping writes nothing;
- a row the seed has not changed since the importer wrote it takes the legacy change (only the differing columns);
- a row changed in both places is left as the seed has it and listed as a conflict. A row only the seed changed keeps the seed's change;
- a value a different seed row already holds under a unique index of the table (a customer identifier the seed's own widget gave another contact, a help article's slug, a participant already on the conversation) is never written. A row the seed holds is left as it is and listed as a conflict; a contact new to the seed is appended without that identifier, with its conversations, messages and files, and listed with the conflicts; the holder keeps its value. A new row of any other table is a conflict, and so is a row of the delta that references a row the seed does not hold (one withheld this way, or deleted), which would break a foreign key. The reason names the index's table and columns and the holder's id, never the value. A value counts as held even when the same delta releases it later, and identity and authority rows (users, devices, grants, delegations) are not checked this way: a new legacy user whose email a seed member already has stops the batch, as before.

A conversation that gains legacy messages is refreshed: the new messages follow its existing messages in transcript order, a delivery id the widget repeated goes to `legacy:<message id>`, and the conversation's revision and last message follow them. The seed's transcript is never renumbered. In a conversation the seed has changed since import, or closed, legacy's new messages and files are held and listed with that conversation's conflict instead of inserted.

**Boundaries.**

- Project rows are the seed's. A delta never writes `projects`, `project_settings`, `email_settings` or `public_project_aliases` (`deleted_at`, website and allowed origin, widget key, every column). It disregards the legacy project's soft delete, so rows new or changed after legacy retires the project map as live rows, and the widget and workspace keep working after the sweep that follows the retire.
- Identity and authority rows (users and their settings, memberships, devices, grants, delegations and their events) are appended when new and never updated: a legacy role change never raises a seed member's permissions. A differing one is listed.
- Erased contacts stay erased, and so do contacts being erased. The rows of a contact with a `contact_erasures` row or a `contact_erasure_leases` row (an erasure in progress, or one that was interrupted and has not been sent again yet) (the contact, the messages and files of their conversations, notes, participants, events) are not applied, their files are not uploaded, and their journal copy is stored redacted (`source_json='{}'`), as erasure leaves it. Erasure itself clears the journal copy of every row of the contact, whatever its status, found by the seed row it mapped to and by its source: the contact and its merged aliases, their conversations (the seed's and legacy's, including ones the seed never held), every row of those conversations, their files (every file linked to their messages, delegations or delegations' internal notes, with each file's variants such as an image preview) and every link of those files, and any row naming the contact; the files' objects are deleted from R2. A delta treats a file as the contact's when any of its links (or its original's, for a variant) is in one of the contact's conversations, through a message, a delegation or an event.
- Mail the seed already took is skipped. When the seed reads the company's mail from Amazon SES ([Email](email.md#receive-mail-that-amazon-ses-stores-in-s3)), legacy may store the same messages too, with the SES message id as the message's delivery id (`local_id`). A legacy message whose delivery id a reader receipt holds (`legacy_mail_s3_receipts.ses_message_id`, any state) is not written, held or listed, and neither are its files (their bytes are not uploaded) and file links. A conversation the seed does not hold yet whose every message in the delta is skipped is skipped with every row of it (participants, events, buckets and the rest); a conversation the seed holds is never skipped, and keeps its revision and last message when its only new message is skipped. Project rows stay kept and erased contacts' rows stay erased; skipping comes next. Each skipped row is journaled with status `skipped`, no target and no source copy (`source_json='{}'`; a rerun compares the digest alone), so a rerun replays it. Without such receipts a sweep imports exactly as before.
- A delta never deletes. A row legacy soft-deleted after its import is journaled archive-only and listed; a row the seed deleted after its import is not brought back. A row hard-deleted in legacy is not detected.
- Applying a delta starts nothing the running app would: every conversation it writes to is fenced from the workflow journal's triggers, as Move in does, and a row a trigger adds to the outbox, mail, notification, integration, job, lead, brand, survey or workflow tables is removed in the same transaction. The batch removes only the fences it inserted: a fence another writer held before the batch (a Move in writing the same conversation id) stays, and the batch's own are gone when it commits.
- A delta never offers a survey. When it sets `resolved_at` on a seed conversation that has a survey cycle (`conversation_tracking`, which the widget's hand-off and other native doors open), the resolution row the seed's trigger adds is removed in the same transaction, so the widget's resolution state offers the customer nothing and the survey dispatcher has nothing to discover. The conversation stays resolved, and the trigger's start of the next cycle in `conversation_tracking` stays. A member resolving a conversation in the seed records its resolution and survey as before.

**Result and reruns.** The command exits 0 when the delta is applied, conflicts included. Its stdout summary adds `delta` (`since`, `watermark`), `appended`, `updated`, `unchanged`, `kept`, `erased`, `skipped`, `archivedOnly`, `withheldObjects`, `ignoredRetireMarker` with `--retire-marker` ([after the retire](#delta-sweeps)), per-table counts (`tables.<table>.skipped` among them) and `conflicts`: `{sourceTable, sourceId, targetTable, targetKey, reason}` entries, ids and reasons only, contacts appended without their identifier among them (`conflictCount` counts them). `legacy_import_conflicts` keeps them. A sweep that stopped partway, for any reason (a refused batch, a lost connection, a stopped process), is resumed by running the same command with the same package: each chunk is its own journal run whose id is the digest of the chunk, committed batches are skipped, every decision is made again from the seed as it is, and the import completes with nothing applied twice, ending as one uninterrupted import would (same business rows, R2 objects and journal). Rerunning a complete one changes no business row, R2 object or journal row and lists the same conflicts.

**Check.** `check.mjs delta` only reads and prints one JSON object of counts:

```sh
node scripts/legacy-import/check.mjs delta --package /private/company/delta-1/import --previous-total N --persist-to .wrangler/state
node scripts/legacy-import/check.mjs delta --package /private/company/delta-1/import --previous-total N --database <installation>-db --bucket <installation>-files
```

It exits 0 only when every row of the delta is journaled by the delta's own runs; the project's journaled source rows (distinct table and id across all its runs, `projectSourceRows`) equal N plus the delta's rows that no earlier run journaled (`newRows`); and every attachment the delta applied is identical in R2 (size and SHA-256; files of erased contacts, of held rows and of skipped messages are withheld by design). It prints `tables.<table>.skipped` and the total `skipped`, `conflicts` (how many the delta's runs recorded) and `conflictRows` (each of them as `{sourceTable, sourceId, targetTable, targetKey, reason}`, ids and reasons only). Each query reads one run, and checks another run's journal row through the journal's source index and that run's own row, so a project with hundreds of runs and a million journal rows reads a few rows per journal row. When D1 answers that it is overloaded (too many resources consumed within its 10-second window) the check waits 2, 4, 8, 16 and 32 seconds before each of up to five retries, printing one JSON line to stderr per retry and counting them in `retries`, then fails with D1's error; any other error fails it at once. N is `projectSourceRows` as the previous check printed it. Before the first sweep, run the check once before the import: it exits 1, as nothing of the delta is journaled yet, and prints the current `projectSourceRows`. `--exclude-table` works as for `rows`.

Sweep again with `--since` set to the watermark of the delta just imported, until the legacy project is retired and a final sweep after its retire finds nothing new.

**The sweep after the retire.** The legacy retire soft-deletes the company's project and, in the same transaction, every live contact of it with one marker time, to the second in UTC, without touching `updated_at`:

```sql
UPDATE projects SET deleted_at='<T>' WHERE id=? AND deleted_at IS NULL;
UPDATE contacts SET deleted_at='<T>' WHERE project_id=? AND deleted_at IS NULL;
```

The operator records `<T>` (for example `2026-11-25 09:30:00`). Every sweep exported after the retire carries every marked contact (their `deleted_at` is new), so import it with the marker:

```sh
node scripts/import-legacy.mjs --package /private/company/delta-9/import --apply --persist-to .wrangler/state \
  --retire-marker "2026-11-25 09:30:00"
```

`--retire-marker` takes `YYYY-MM-DD HH:MM:SS` (UTC, as the retire records it) or ISO-8601 UTC (`2026-11-25T09:30:00Z`, optionally with `.fff` milliseconds), with `--persist-to` or `--remote` alike. Any other value, the flag with `--file`, or the flag with a full package is refused before anything is read from or written to D1/R2. In that delta a contact whose `deleted_at` is the same instant as the marker is read as the same row with `deleted_at` null: it updates nothing in the seed and makes nothing archive-only, so a marked customer's new message in an existing conversation and a new conversation with its messages import as live rows, and a marked contact whose only legacy change is the marker is `unchanged`, even when the seed changed it. A marked contact with other legacy changes gets the usual decision for those. A contact deleted at any other time keeps the usual handling (archive-only, listed when the seed holds it, its conversations and messages archive-only), and a row's own `deleted_at` still makes it archive-only. Archive-only never follows the project's soft delete, so the workspace, its settings and the widget stay live. The summary counts the marked contact rows as `ignoredRetireMarker`, top level and in `tables.contacts`, whatever else is decided for them; without the flag it is absent.

Import every sweep after the retire with the marker from the start. A run without it lists the marked customers as conflicts and leaves their new messages out, and the marker makes each contacts chunk its own journal run (its run row records `retireMarker`), so a later run of the same package with it adds runs that `check.mjs delta` counts twice. If that happened, export a fresh delta with the same `--since` and import it with the marker. Without the flag nothing here changes: a delta imports exactly as before.

## Deliberate boundaries

Omitted: `ai_logs` (operational model request/response logs), page views and collector/tracking events, auth/pairing handshakes and empty prompt-plan caches. Exported conversation event types are `INTERNAL_NOTE`, `AGENT_ASSIGNED` and `USED_INSIGHT`: the support cases rendered by the legacy conversation UI. Assignment/insight history maps to native attributed transcript events; current status and participants come from their durable rows. Event media follows the retained event scope. Delegations, progress events and project device settings have native fields and import with authority disabled; their media remains in the archive/R2.

Archive-only: read/notification maps, connection/proxy state, leads, AI thinking/optimizations, legacy billing/account fields, non-payload collector and summary metadata, provider-only dataset references, non-message media associations, pending invites and deleted rows. Retain these in the private original bundle and `legacy_import_rows` for later decisions. No jobs or provider requests replay. Retained dataset markdown maps only when publication provenance permits it. AI profiles use an explicit chosen native model and original/default prompts. Plugins retain their configuration but must be reviewed before use.

Build before cutover: rewriting article inline media/avatar/background URLs to authorized native object URLs; translating unsupported legacy widget overrides/defaults and availability behavior; recreating live mail/provider/integration configuration with native credentials. Legacy access tokens, passwords and encryption keys are deliberately dropped, not migrated. Redis sessions/cache, open sockets and SQS execution state are dropped; durable conversations and support content come from MySQL/media, not Redis.

## Local integration

`pnpm run test:legacy-export` requires an isolated local/CI MySQL admin supplied by `LEGACY_TEST_MYSQL_HOST`, `LEGACY_TEST_MYSQL_PORT`, `LEGACY_TEST_MYSQL_USER`, `LEGACY_TEST_MYSQL_PASSWORD`, optional `LEGACY_TEST_MYSQL_SOCKET`. It creates and deletes only its randomly named test database/user. It loads the complete migration-derived final schema (53 tables and 580 columns from the live shape, with synthetic rows only) and realistic ChargeDesk/12ui fixtures, grants a SELECT-only reader, runs both exporter commands, invokes the importer's public command twice per project and checks actual local D1/R2 content, privacy, publication, tenant separation and replay. It then changes one project in the legacy database (new and late messages, a new customer with a file, a renamed contact, the project retired) while the seed's team changes a conversation, exports a delta `--since` the recorded watermark, imports and reruns it, and runs `check.mjs delta --persist-to`. `LEGACY_TEST_OUTPUT` keeps synthetic artifacts outside the checkout for local UI inspection. CI runs this single integration test against MySQL 8.4.
