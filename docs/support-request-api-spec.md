# Support-request API specification

A workspace owner/admin issues a named machine credential for one source product or agent (for example a handoff from Handset) and binds it to exactly what it may touch; the scoped workspace API then lets that product create a ticket and append to it without a human session. Credentials are extensions of the CONNECTIONS-001 token model, not a second system: bearer-only, no cookies, no CORS, secret shown once at issue and stored only as a hash, with a non-secret display prefix, name, source-product label and the issuing member, creation time, optional expiry (UTC), last-used time and last-used source visible in Settings. Issue, rotate and revoke require the current owner/admin with step-up; rotation issues a new secret and keeps the old one valid for an owner-chosen overlap (default none, maximum 7 days) before it retires, and revocation, expiry, a blocked or deleted workspace and a restore take effect on the next request, with an in-flight create either committed whole or refused with nothing stored. Scopes are separate and narrow: `conversations:create`, `conversations:read` (bound by default to the conversations the credential created), `messages:append` (customer-side message or internal note on a conversation inside its bounds) and, unchanged, the existing operator-style `messages:write`; a read-only, a create-only and an append-only credential can each be issued, and no scope implies another. Bindings limit the credential to named brands, mailboxes/sender addresses, groups, request forms and an API channel label (`api:<source product>`, a first-class channel in inbox filters, reports, SLA and triage); it may set only priority levels and existing workspace tags its bindings allow (an unknown tag is refused, never created), may not assign, choose status beyond New, write internal-only fields or act as an operator, and an operation outside its bounds returns 404 for another resource and 403 `outside_credential_bounds` for a disallowed value, never a silent adjustment. Create takes a requester identified by email, E.164 phone or the caller's own external ID (namespaced to its source product) with optional name; subject, plain-text body and attachments passed by reference (a prior bounded upload id or a public HTTPS URL fetched under the existing egress rules with a required SHA-256, no redirects, size and 10-second bounds and the widget's type rules, the whole request atomic so one bad attachment stores no ticket); source channel label, priority and tags; and a source-product reference `{product, ref, url}` where the product label is fixed by the credential and cannot be spoofed, the URL is HTTPS without embedded credentials and is shown to operators as a back-link ("Created via Handset, open in Handset") and never fetched, and a second create for the same source reference under a different key returns 409 `source_ref_exists` with the existing ticket ID so the caller appends instead. The `Idempotency-Key` header is required on create (1-200 characters, scoped to workspace and source product so a rotated or reissued credential still deduplicates, retained at least 30 days): the same key and canonical body return the original status and body marked as a replay, a different body returns 409 `idempotency_conflict`, and a key still in flight returns 409 `in_progress` with `Retry-After`; append is idempotent by the existing `localId`. The identity rule is CUSTOMER-001's: a requester matches an existing contact only by an exact verified key, a new contact created by the credential is marked as asserted by that credential and unverified, email or name text alone never grants history access or merges contacts, two identifiers that point at different contacts return 409 `identity_conflict` without disclosing either contact, a requester matching an erasure tombstone is refused with `identity_erased`, and responses have the same shape whether or not the contact already existed. Append posts a message to an existing conversation as the requester (kind `customer`) or as an internal note (kind `note`), never as an operator or as AI; a `customer` message reopens a Solved ticket and creates the linked follow-up of a Closed one under STATUS-001, a merged ticket answers 409 `merged_into` with the surviving ID, and attachments follow the same reference rule. API-created tickets are untrusted customer content: they pass the same triage, automations, routing and AI-agent rules as any new ticket with source `api`, and body text, subject and source fields can never instruct the agent or open an external effect. They respect spam, abuse and consent: blocked senders, blocked identities and per-requester create caps (default 5 per hour, owner-configurable) place the request in Suspended under MAIL-002 with a reason and a 202 `held_for_review` response and no ticket-created event, AI request or outbound message; acknowledgments and any customer-facing send follow NOTIFY-001 and CHANNELS-001, an email acknowledgment is sent only when the caller supplies a consent record (channel, basis, time) the workspace accepts for that source, an SMS or WhatsApp send needs recorded opt-in and an approved template and an opted-out number is refused while the ticket is still created, and a created ticket otherwise contacts nobody. Signed webhooks use the existing `integrations.webhook.v1` signing, delivery and retry policy and add `conversation.status_changed` (ticket ID, previous and new status category and ID, source reference) and `conversation.assigned`; a destination can be limited to tickets created by one credential or one source product, and events keep carrying identifiers and values, never transcript text, email addresses or phone numbers. Limits are explicit: the existing per-credential requests-per-minute limit plus a separate create quota per minute and per day configured on the credential under workspace and installation ceilings, and the per-requester cap, each refused with 429, `Retry-After`, `RateLimit-Limit/Remaining/Reset` headers and a machine-readable code naming which limit (`credential`, `requester` or `workspace`); oversize bodies return 413 `payload_too_large` and unsupported types 415, nothing is silently truncated or dropped, and storage or plan exhaustion returns 503 `unavailable` with `Retry-After` and no partial ticket. Errors use the existing `{error:{code,message}}` shape with stable codes. Every action is audited under AUDIT-001 with a machine actor named on the credential: issue, rotation, scope or binding change, first use, expiry, revocation and denied attempts (counted per credential and window, not one event per probe), and every create or append records the credential name, source product and reference, request ID, idempotency-key digest and outcome in ticket history ("Created by API credential Handset support handoff"), never presented to the customer as a person, and the credential's name survives its revocation while an erased issuer is redacted without losing the event. Erasure under ERASURE-001 removes personal content from API-created tickets, stored replay bodies, pending event payloads and attachment bytes, keeps an opaque tombstone and the source reference without personal data, and fences a stale replay or a later create from resurrecting the identity. Portability under PORTABILITY-001 exports API-created tickets with channel label, source reference and machine-actor name, and exports credential metadata (ID, name, source product, scopes, bindings, creation, expiry, revocation, last-used) without hash or secret; restore creates every credential revoked and inert so the receiving owner must reissue, carries idempotency records as key and body digests only, and replays nothing. Documentation (`docs/api.md`) lists the new operations, scopes, bindings and error codes with runnable examples that keep tokens out of command arguments.
