All paths are in src/modules/legacy-import/adoption unless stated otherwise. None of these routes are mounted by src/app.ts or move-in/routes.ts on this candidate. Existing product v1 remains synthetic and source==custody only.

## Approval and native first-owner authority

- routes.ts: `createLegacyAdoptionRoutes(readReview?: AdoptionReviewReader): Hono<AppEnv>`; mount below `/api/move-in` after native DB middleware and explicitly classify its two routes as `data.import` in C's owned route-permissions file. The implementation also calls native `requireActor`, the first-owner predicate, `memberAccess(...).permissions.has('data.import')`, exact-origin approval and `requireStepUp` itself.
- `GET /projects/:projectId/legacy-import/:sha/adoption`: first installation owner in the ORIGINAL setup workspace only; counts/IDs/collision category/approval version, no source directory, email, session hash or content. `projectId` is custody/setup, not destination. Counts include historical staff/memberships and an explicit no-access qualification.
- `POST /projects/:projectId/legacy-import/:sha/adoption/approve`: exact `{approvedManifestSha256, sourceProjectId, policyVersion:2}`; same Origin required for bearer as well as cookie requests; recent native step-up. Returns 202 and `requiresPreflight:true`. This reserves/renews approval, never creates a project or enqueues canonical work. C's start schedules bounded preflight; approval alone does not do work.
- `AdoptionReviewReader = (env, sha, custodyProjectId) => Promise<{manifest: LegacyPackageManifest, sourceRetentionDeadline: number|null}>`. C must supply B's current ready-custody read with all generation/retention/erasure predicates. The default `readAdoptionManifest` is a real immutable R2 checksum reader for contractVersion 2, source project count exactly one and exporter ordinal filenames. Its retention deadline is null because A does not own B's registry. It refuses v1 metadata; do not relabel existing v1 packages.
- authority.ts: `requireInstallationOwner(c, setupProjectId) => {actor, principal}`; `firstOwnerPredicate(principal): SqlGuard`. Principal fields: actorId, sessionHash, setupProjectId, expectedEmail. Expected email comes only from installation configuration; it never chooses the principal.
- Original setup evidence is native owner_setup.claim_id plus exactly one successful dashboard owner.created audit project for that user. The live session must still select that original workspace with owner membership. A present Business link must agree. Missing/sentinel/ambiguous evidence returns installation_owner_binding_required; no upgrade repair/backfill is supplied by this round.

## Stored approvals, worker fences and core

- store.ts: `getAdoption(db, sha)`, `approveAdoption(db, principal, sha, sourceProjectId)`, `mappingProfile(record)`, `readActorOrigins(db, projectId, targetTable, targetId)` (only after caller authorizes that exact native read).
- `adoptionApply(env, sha, fence): Promise<AdoptionApply>` reads stored approval. Fence is `{runId, version, leaseToken, workspaceToken, approvalVersion}`. workspaceToken MUST be the actual destination/source workspace legacy_delta_leases token. `version/leaseToken` are the claimed v2 worker run; approvalVersion must match the current stored approval.
- Run DB invariants: contract_version=2; project_id stays ORIGINAL custody/setup; source_project_id stays destination; manifest/actor/session/version/running claim must match current approval; claim and workspace lease must remain DB-clock live. This differs from v1's equality-based runAuthority/workspaceLease: C must implement the v2 split, never merely change a URL ID or relax source validation.
- `AdoptionApply = {profile, assertion(db), creation(db, normalizedCreationTargets)}`. Pass this stored capability as `options.adoption` to `importLegacy` or `importDelta`. Planning accepts `planImport(...,{mappingProfile: profile})`. Do not construct a policy from manifest JSON or accept one from HTTP.
- The creation targets carry the exact written project/settings projection; later batches and resumed invocations assert that projection, and native edits refuse. The core repeats adoption assertions inside canonical+journal batches and commits `creation(db, normalizedCreationTargets)` only with the actual source-mapped projects/settings group. Creation records provenance, inserts exactly the approving native owner membership and calls `legacyWorkspaceDefaults`. No stub project or auth/Business rewrite.
- C must compose adoption authority with B's package scope-generation fence in EVERY scratch/canonical/object/checkpoint/cleanup-authority transition, and capture whole-installation work baseline BEFORE the creation batch. This A capability does not replace B custody.
- Stored `HistoricalAdoptionProfile`: `{kind:'historical-adoption', policyVersion:2, manifestSha256, custodyProjectId, sourceProjectId, custodianId}`. Original chunk identities/digests stay unchanged. `legacy_import_mapping_profiles` binds their interpretation atomically; a previous v1 journal cannot become v2, and a v2 journal cannot be replayed as CLI/native-account mapping.
- scope.ts: `validateAdoptionScope(bundle, context, profile)`, `preflightAdoptionTargets(db, profile, targets, available?:Set<string>, checkReferences?:boolean)`. The latter checks primary-target provenance, all full unique indexes including historical identity targets and FKs. `available` is previously validated mapped parent identities for package-wide preflight, not arbitrary native IDs. Build it with existing d1.identity. Core check-only also checks current target ownership/unique keys; complete inter-part FK validation and the all-parts barrier belong to C before objects/canonical apply. Current bounded core apply checks actual FK availability again.

## Historical interpretation and source closure

- Source users/user_settings/project_users/memberships and global ai_defaults archive without native user, credentials, membership, setting or global configuration writes. Originals/roles/deletion flags stay in legacy_import_rows, including archived_only counts.
- Human messages preserve source actor IDs and add move_in_message_sources author_json. Notes/INTERNAL_NOTE events use move_in_notes author_json, source_time, original ID, text, bucket_id and the existing private attachment link table.
- The v2 source closure must include the single source projects row, original user rows and relevant project_users/memberships (for original role snapshots), conversations/contacts, and event/media pivots. Existing v1 Worker hydrate currently loads users but omits membership role context; C must add it without an unbounded staff/history load.
- historicalNoteMedia reuses mapCore for media, deriving its conversation from the original Event pivot, and writes move_in_note_media. Cross-conversation note sharing currently fails closed with unsupported_note_media_scope. Native note URLs/downloads are exercised for a single-conversation synthetic attachment.
- Current native assigned_to is NULL; source assignment is in legacy_actor_origins. Macro created_by is the native custodian, with original creator in that table. Revoked device/job principals and media staff-upload IDs are namespaced; no source session/capability is restored. Source AI profiles are disabled.
- readActorOrigins exposes only `{field,source_user_id,display_name}` under the requested project/target. Existing source journal retains all other original fields. C's normal details UI may annotate; historical actors never become member/assignee options.
- `management/provisioning/legacy-workspace.ts`: `legacyWorkspaceDefaults(env, projectId, guard): D1PreparedStatement[]`, exported only from provisioning/index.ts. It shares creationCondition; source settings win, absent settings get inert defaults, system workflow stays draft. No starter, sender, mailbox, owner alert or after-commit work.
