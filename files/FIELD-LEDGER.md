### What comes across from Zendesk and what does not

Written by Run Edit Run fleet, 2026-11-17. This field ledger describes a wholly invented 200-customer, 300-ticket workspace. **Dropped** means it has no working field here, even when the private original keeps it. Erasure still removes private source custody. Never treat retained JSON as a usable replacement for the old feature.

Zendesk Admin Center offers **JSON, CSV and XML** exports in a ZIP. Its JSON files contain newline-delimited singular records such as `{"ticket":{...}}`; the official guide also documents `{"tickets":[{"ticket":{...}}]}`. Move in accepts those layouts, arrays of singular wrappers, and API JSON collections such as `{"users":[{...}],"next_page":null}`, including pretty-printed files. Existing JSONL/NDJSON keeps working. CSV and XML are not accepted. CSV lacks comments and descriptions and uses the account timezone; do not rename it to JSON.

The API returns tickets without their conversation. Gather every comments page and the referenced users, and use the local packer below to bind comments/audits to their ticket IDs. A bare API ticket with no comments is refused; its description is never substituted for the missing conversation. The admin export itself can omit comments for tickets over 1 MB. These also need complete comment files. Current per-upload and per-record limits still apply; split at whole-ticket boundaries. File import does not retrieve another page or download any URL. API list pagination describes only the supplied page, so gather all pages before moving. Macros, rules, forms, views, SLA policies, identities and Help Center content are separate API objects; the Admin Center JSON export is not a full backup of those features.

Before approving, review these losses:

- **People:** alternate email/phone identities, locale and timezone preferences, notes/details, custom user fields, external IDs and source suspended/deleted state are not native contact fields. The primary phone is kept. Source verification, roles and membership access never grant access here. Suspended/inactive source people remain unverified historical contacts; review native blocking before using them.
- **Ticket collaboration and outcomes:** CCs, followers, satisfaction scores/comments, custom status labels, form/brand links, problem/follow-up relationships and merge relationships are not recreated. A merged source remains its own closed history, and its explicit merge comments survive. It is not joined to the target. Source recipients and ticket metadata remain source-only.
- **Files and conversation presentation:** local supplied bytes are verified and kept with their message or private note. URL-only files remain missing bytes. Download URLs are removed by packing. Comment metadata, voice recording/call controls and HTML presentation are not recreated; supplied voice/chat transcript text comes across as ordinary historical messages.
- **Configuration:** unsupported field types (partial credit card, lookup and multi-lookup), extra company memberships, group memberships/default routing, view columns/grouping, source access restrictions and unsupported rule/macro semantics do not become working settings. Numeric field strings become numbers only under a numeric definition and within native precision; unsafe values refuse the ticket. Rules arrive as drafts, forms disabled, views personal. SLA policies need an explicitly reviewed calendar and stay inactive when supported.
- **Knowledge and historical reporting:** Help Center sections, placement, translations, source article authors, locale, labels and presentation do not come across. Restricted articles are held back whole. Historical audit/metric data stays inert where supplied; imports never create a satisfaction survey, SLA clock or native Reports cohort.

Recommendation: keep a secure export outside this product until you have reconciled collaboration, ratings and merge history. Recreate the collaborators and owner-approved blocking/routing you still need using the product's existing controls. Evaluate satisfaction history and unsupported relationship fields separately before retiring Zendesk. No schema migration or new feature is introduced to hold them.
