# Legacy package grant reader

The signed `happytohelp-legacy` namespace accepts only an entire
`happytohelp-legacy-chunks-v1` database snapshot inside `rer-door-package/1`.
It is separate from the owner-facing vendor selector. The source project's
references bind to the server's claimed destination; source configuration does
not replace the workspace, claim, trust or owner. An existing owner's matching
source identity is reused; conflicting identities or roles refuse the package.

The sender sends `rer-package.json` first. Until every verified segment is in
the admitted installation and namespace, planning answers
`409 package_segment_missing` and creates no plan. Each segment/request retains
its original grant's 2 MiB and 32 × 64 KiB envelope and needs a fresh single-use
grant. Segmenting is transport, never separately approved record waves.

This is an eager reader: the accessor materializes a requested file and the
reader returns the entire logical record array. Legacy parsing allows a 16 MiB
aggregate package, at most eight segments, 16 MiB per file and 1 MiB per source
record. The exporter's normal 4 MiB JSON parts fit; its optional 32 MiB parts exceed this runtime's allowance. The reader also bounds the eager source/projection working set before kit planning; unsupported sizes refuse the
whole snapshot. Zendesk retains its separate 2 MiB / 5,000 / 128 KiB raw parsing
and 48 KiB / 20 supplied-attachment bounds. Neither source changes grant, D1,
native-set, request or plan limits. Larger legacy snapshots remain unqualified;
157,478 conversations cannot fit a 100,000-record grant.

Every primary row, object and manifest is accounted for separately; context
copies do not inflate primary counts. Inner and outer counts, independent
snapshot counts, projected context, provenance, indexed paths, file bytes and
digests, and complete media/key/file ownership must agree. Pure `mapLegacy`
provides the mapping. Every expanded native row and 64 KiB byte chunk counts
against the effective record grant before publishing mapping results. Reused plans,
Apply and Undo also check the current action grant; an earlier larger grant cannot
supply authority to a later smaller one. Unknown
or deleted rows retain their explicit archive-only disposition. Financial values
remain exact history, pending external work stays held, old credentials are
refused and imported mail stays disabled.

Native rows and bytes use the existing kit planner, fingerprint approval,
lineage, apply journal and strict Undo. Each typed SQL target guards its full
value, absence and owned-set cardinality. An atomic historical-write fence
prevents live mutation triggers from creating unjournaled context changes,
history, jobs or alerts; every dependent imported row is an explicit effect.
Normal native writes retain their existing triggers. A legacy media key requires
complete verified D1 chunks after the ordinary ticket/contact/private-note
authority check; missing custody never falls through to R2. Existing R2 objects
are unchanged.

Catch-up is another complete cumulative database snapshot, including changes
since 16 October. There is no partial-delta wire format. Relationship-derived
values enter source fingerprints; unchanged targets are reused, replacements
and conflicts are explicit, and missing source rows are reported and retained.
Retained native message ordering stays in the relationship context when a source
message disappears or becomes archive-only; it is not another primary source row.
Surviving messages therefore keep a complete retained transcript without compacting
their revisions onto a retained message's unique slot. Historical ledger, usage,
operation and reconciliation-hold values cannot be replaced by catch-up. Planning
refuses changed values, and Apply fences every financial value atomically, including
approvals saved by the previous reader. Exact kit Undo can still restore prior images;
native contact erasure keeps its existing precedence.
Undoing a catch-up restores its preceding snapshot before the initial import
can be undone. Later native edits or shared references refuse strict reversal.

Exact package files remain byte-preserved in scoped transport custody. Base's
package API records artifact metadata, rather than claiming kit-original bytes
it did not retain. Native erasure withdraws transport, snapshots, plans,
journals, portable copies and affected native byte chunks, including unapplied
packages. Hash-only alias fences cover context, archived/rejected rows and
object metadata, and corrected uploads cannot restore erased identities.
Equivalent authorized transport copies are subject to the bound Base cleanup;
foreign scopes remain separate. Portable restore disables the grant door and
keeps the existing exclusions for live sessions/device/execution authority.

This source slice is not migration, release, cutover or large-source
qualification. The saved Base/native predecessors, adopted-source reconciliation,
independent frozen packet and original source holds remain separate obligations.

Receiver/cleanup adoption uses only `package.ts`, `types.ts`, `planning.ts`,
`admission.ts` and `handler.ts` from saved Base source
`5dd6b3c170dd50e494008e4b8f80050a6ff36e14`. Those bytes are separately recorded;
other selected Base sources and HH adaptations retain their provenance. The
bound donor is SAVED/unqualified, not accepted or integrated.

## Nonapplying native work-unit compiler

`prepareLegacyUnits` in `units.ts` uses the actual package decoder and
`prepareLegacy`, including retained native transcript context, constraints,
immutable financial history and the complete native-set preflight. It reads the
installed foreign-key schema and retained lineage anchors, then calls the pure
`compileLegacyUnits`. It does not index custody, save a plan, apply SQL or emit an
import receipt. The ordinary package source still owns its identity indexing.
No existing route uses this compiler. It is not an over-cap or census reader:
the complete 157,478-record source still refuses the 100,000-record allowance.

Every prepared source identity and its complete MappingResult stay together.
Conversation/transcript and path-bound media/object/pivot closures coalesce;
knowledge publication pointers, versions, documents, category links and article
snapshots coalesce. Shared contacts remain separately owned dependencies. The
compiler resolves installed foreign keys and explicit soft references from the
prepared values, and uses existing Relationships/blob context for source media
custody. Only the current project/owner and actual retained same-lineage native
rows can be external anchors. Missing, foreign, ambiguous or unsupported
references, cycles outside declared atomic closures, and over-bound indivisible
groups refuse the compilation. There is no remainder or guessed order.

Unit keys hash sorted source identities. Each unit has a dependency-first order,
relationship digest, native projection digest and full fingerprint, committing
its mapping dispositions, aliases, files and dependency fingerprints. File
custody is assigned once even when a file contains rows from several units;
context copies and archive/rejected/metadata identities are separate aliases.
Repeated opaque blob aliases have one deterministic owner and retain all their
file references. They do not grant shared-object or subject authority.

The native projection reads the real target adapter's inert SQL descriptions.
It counts both the business/chunk row and its `legacy_door_targets` origin row,
including hold rows and the origin's duplicated chunk value. `storedBytes` is
readable UTF-8 canonical JSON of the adapter's supplied column image, plus the
fixed SHA-256 width of the kit-assigned origin revision; it is not a SQLite file
allocation estimate. Origin fingerprints commit source-derived fields, excluding
the future job revision. `blobBytes` counts decoded object bytes once in their
chunk rows; encoded copies are included in native stored bytes. Kit journal and
transient historical-write-fence rows are separate. These definitions permit
comparison with the actual native storage door without inventing a future job.

The returned `unit` and `native` shapes are structurally useful to the fixed
Base 8ff `WaveUnit` and `WaveNativeRow` interfaces. No bounded-source adapter,
authority predicate, census, approval, grant, migration or runtime is installed.
The existing ordinary engine does not acquire cross-entry atomicity from these
arrays. Later adoption must honor indivisible closures within its qualified
transaction/checkpoint bounds, retain all existing native/erasure/Undo guards,
and reconcile its exact installed native rows and runtime metadata. A complete
nonapplying parent, finite approved budgets, separately approved ordered
immutable children, one lineage, the previous complete head while partial, and
all-child reconciliation with readable bytes and the gone boundary remain
separate conditional obligations. Source/stack/review and release holds remain.
